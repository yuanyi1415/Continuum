# 01｜产品定义与边界

## 1. 用户真正的问题

长期 AI Coding 项目中，随着：

- Session 增多；
- Spec / Ticket / ADR / 文档增多；
- Coding Agent 反复切换；
- Agent 在实现中继续发现新问题；
- 项目长期演进；

人和 Agent 会逐渐失去共同认知：

> **项目现在到底是什么？当前正在改变什么？哪些东西是权威？我接下来应该相信和阅读什么？**

Continuum 解决的是这个问题，而不是“文档不够多”。

---

## 2. Continuum 是什么

Continuum 是：

- Project-scoped Lifecycle Control Plane；
- 长期项目的 Current State Authority；
- Artifact / Change / Relation 的轻量索引；
- 跨 Agent 的工作连续性层；
- 实现后全局收敛的 Reconcile 层；
- 最小有效 Context 的路由层。

---

## 3. Continuum 不是什么

Continuum **不是**：

- Coding Agent；
- AI Coding Runtime；
- Spec 工具的替代品；
- Ticket 系统的替代品；
- TDD / Review 方法论；
- Workflow Engine；
- 多 Agent Scheduler；
- 文档管理系统；
- 全局 Memory 系统；
- RAG / 向量知识库；
- IDE；
- Web Dashboard。

---

## 4. 与 Matt Pocock Skills 的关系

### Matt 负责

```text
Domain Understanding
→ grill / research / prototype / wayfinder
→ to-spec
→ to-tickets
→ TDD / implement
→ code-review
```

### Continuum 负责

```text
Current Project State
→ Change Lifecycle
→ Artifact Authority Index
→ Context Routing
→ Work Binding
→ Lifecycle Trigger
→ Reconcile
→ New Project State
```

两者关系：

> **Matt 是 Development / Discovery Engine；Continuum 是 Project Control Plane。**

Continuum 不 fork、不改造、不复制 Matt 主流程。

---

## 5. 什么时候应该使用 Continuum

只有当工作开始具备明显“项目性”时才值得启用：

- 会持续多个 Session；
- 存在多个 Change；
- 需要长期项目认知；
- 需要 Agent / 人之间接续；
- 需要阶段收敛与历史追溯。

### 非项目任务

例如：

- 解释一段代码；
- 临时 SQL；
- 一次性脚本；
- 查报错；
- 小 PoC；
- 普通开源项目阅读；

默认不使用 Continuum。

---

## 6. 激活原则

```text
没有 .continuum/
→ Normal AI Coding
→ Continuum 完全静默

存在 .continuum/
但当前没有正式 Work Binding
→ Project Aware
→ 临时问答继续静默

存在明确 Work Binding
→ Managed Work
→ Lifecycle / Reconcile 生效
```

### 核心原则

> **Project Opt-in + Work Explicitly Bound。**

但“Explicitly Bound”不意味着增加额外仪式。

例如：

```text
/implement P03
```

已经表达了明确工作意图，就不应再要求：

```text
continuum manage P03
```

---

## 7. 最终用户心智

用户不应该感觉自己同时在维护：

```text
Matt
Codex
OMP
Continuum
Git
...
```

理想心智是：

```text
我正常开发
  ├─ Matt 帮我把事情拆对
  ├─ Codex / OMP 帮我执行
  └─ Continuum 帮我别把项目弄丢
```

> **如果用户需要每天记得“维护一下 Continuum”，产品设计即失败。**
